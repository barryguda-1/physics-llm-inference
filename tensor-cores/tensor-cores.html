Tensor Cores:
whole matrix tiles retire in a single cycle

A tensor core is a hardwired matrix multiply-accumulate unit: D = A×B + C on 4×4 tiles, all 64 multiply-adds in one clock cycle. An H100 packs 528 of them, which is how the same die that does ~67 TFLOPS on CUDA cores reaches ~2000 TFLOPS on fp16 matrix math — and Blackwell's 5th-gen tensor cores push the same math another 10× at FP4. The catch: strict dtypes, aligned memory, and multiple-of-16 tiles — miss them and you pay double-digit percentages.

Section 1

01One core, one cycle: the multiply-accumulate

Everything a tensor core does is one operation, done at absurd width: take two small matrices and an accumulator, multiply and add them all at once. The 4×4×4 MMA is the atom — 4·4·4 = 64 multiply-adds = 128 FLOPs per cycle, per core. Compare that with a CUDA core, which retires one scalar FMA per cycle and needs 64 cycles for the same tile.

// the atom every tensor-core instruction is built from
for m in 0..3:  for n in 0..3:          // 16 outputs
    D[m][n] = C[m][n]
    for k in 0..3:                      // × 4 terms each

A 16×16×16 WMMA tile is the same loop with 16s — 4096 FMAs = 8192 FLOPs per instruction.

Section 3

03The throughput ladder: 67 → 2000 → 4000 TFLOPS

Same chip, three very different ceilings. The CUDA cores are general-purpose; the tensor cores only do matrix math, but they do it 30–60× faster. This is why inference converts every hot op it can into a batched matmul.

Fine print: bars use NVIDIA's headline numbers, which are sparse-inclusive — dense is half (H100: ~990 dense FP16 / ~1980 FP8). The 4×4×4 primitive is the unit of work: Hopper's cores issue larger 64-wide warpgroup MMAs per cycle, which is how the chip reaches its full spec. B200 figures are NVIDIA's GB200 NVL72 spec ÷ 72 per GPU; HGX B200 SKUs run a notch lower (~2.25 / ~4.5 / ~9 PFLOPS dense). Blackwell Ultra (GB300, 2025) lifts dense FP4 to ~15 PFLOPS per GPU. Next stop: Vera Rubin, announced for 2H 2026 — HBM4, with NVFP4 moving into training too.

Section 4 · Walkthrough

04Driving them: fragments in, mma_sync, fragments out

You can't issue tensor-core ops from plain CUDA C++. You reach them through WMMA intrinsics (what's below), cuBLAS / cuDNN, or Triton — which generates them for you. WMMA works on 16×16 tiles: load fragments into registers, run one instruction, store the result.

using namespace wmma;
wmma::fragment<wmma::matrix_a, 16,16,16,
                half, wmma::row_major> a_frag;
wmma::fragment<wmma::matrix_b, 16,16,16,
                half, wmma::col_major> b_frag;
wmma::fragment<wmma::accumulator, 16,16,16, float> c_frag;

wmma::load_matrix_sync(a_frag, a_ptr, lda);  // → registers
wmma::load_matrix_sync(b_frag, b_ptr, ldb);
wmma::fill_fragment(c_frag, 0.0f);           // the "+C"

wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);  // ← tensor cores

wmma::store_matrix_sync(c_ptr, c_frag, ldc,
                        wmma::mem_row_major);

One mma_sync on a 16×16×16 tile = 4096 multiply-adds = 8192 FLOPs in a single instruction. A real GEMM loops this over K-tiles and sweeps many M×N tiles — which is exactly what cuBLAS and Triton unroll for you.

05The odd-size tax: 1024 hits 120 TFLOPS, 1025 drops to 80

Tensor cores want tiles that are multiples of 16 and memory that's aligned. When a dimension isn't, libraries pad it — and lose 128-bit vectorized loads along the way. Drag the size and watch two separate taxes appear: padding waste (small) and row misalignment (the expensive one).

def compare_matmul_sizes(n):
    a = torch.randn(n, n, dtype=torch.float16, device="cuda")
    b = torch.randn(n, n, dtype=torch.float16, device="cuda")
    start = torch.cuda.Event(enable_timing=True)
    end   = torch.cuda.Event(enable_timing=True)

    start.record()
    for _ in range(100):
        c = torch.matmul(a, b)
    end.record()
    torch.cuda.synchronize()

    elapsed = start.elapsed_time(end) / 100      # ms per matmul
    return 2 * n**3 / elapsed / 1e9              # TFLOPS
⚠ Where odd sizes come from: vocabulary sizes. GPT-2's 50257 → padded to 50272 (next multiple of 16). A few padded embedding rows cost almost nothing; a misaligned leading dimension taxes every GEMM against that matrix. Pad once, at load time.

WMMA's own contract makes this explicit: the leading dimension (ldm) passed to load/store must be a multiple of 16 bytes. At N=1025, rows stride 2050 B — not a multiple of 16 — so fragments can't load the fast way at all. The model bar divides throughput by 1.5× when any row is misaligned, which reproduces the measured 120 → 80 drop.

Section 6

06Four habits that keep the tensor cores fed

You will almost never write wmma::mma_sync in production. Your job is to hand the libraries shapes and dtypes they can feed the cores with — and to notice when you haven't.

dtype 101

Ride the right dtypes

Tensor cores speak fp16, bf16, int8; Hopper added fp8; Blackwell's 5th-gen cores added fp4 (NVFP4 / MXFP4) — each step down doubles the math again. Plain fp32 matmul doesn't touch any of them unless you enable TF32. Keep weights and activations in bf16/fp16, quantize to fp8/fp4 where accuracy allows, and check torch.get_float32_matmul_precision() if a legacy fp32 path is slow.

fp32 · cuda cores→bf16 / tf32 · 30×→fp8 · 60×→fp4 · 250× (Blackwell)

Pad odd dimensions to multiples of 16

Vocab 50257 → 50272. Seq len 1025 → 1040. Padding waste at one tile edge is ~1%; the misalignment it fixes is a 33% throughput drop. Pad at weight-load time, once, not per batch.

50257→pad 15 rows→50272 ✓ aligned

Reach for libraries, not WMMA

torch.matmul, cuBLAS, cuDNN, and Triton's tl.dot all emit tensor-core instructions automatically, with the tiling, swizzling, and K-loops done right. Hand-written WMMA is for exotic fused kernels — and even then Triton usually gets there first.

torch.matmul+tl.dot→mma.sync, for free

Bench the shapes you ship

Power-of-2 toy benchmarks hide the tax your real shapes pay. Run the compare_matmul_sizes bench with production dimensions — vocab, seq, batch × head counts — and compare achieved TFLOPS against the ~120 fp16 reference before blaming the kernel.
