GEMM: why matrix multiply is
the workhorse of deep learning

C = A @ B is one line of code and nearly all of a transformer's math. This page builds the intuition from scratch: what one output element costs, why FLOPs grow as n³ but memory only as n², and why that makes big GEMMs compute-bound on an H100 — which is exactly why prefill and decode behave so differently.

Section 1 · Animation

01One output element = one dot product

Strip away the jargon and a matmul is a machine for computing dot products: to fill in one cell of C, take a row of A, a column of B, multiply them pairwise, and add up the K results. That's it. Watch it happen cell by cell — then remember the GPU computes all cells at once.

This toy has arithmetic intensity 192 FLOPs ÷ 128 bytes = 1.5 FLOP/byte — memory-bound! Real model GEMMs (n = 4096) reach 1365. Matrix size is what makes GEMM compute-bound — that's section 2.

# the whole operation, in one line of torch
c = torch.matmul(a, b)          # a: (M, K)  b: (K, N)  ->  c: (M, N)

# what each output element really is:
c[i, j] = sum(a[i, k] * b[k, j] for k in range(K))   # K multiply-adds

Total cost: M·N dot products, each K long → 2·M·N·K FLOPs. At 4096³ that's 137 billion FLOPs — 16.7 million dot products, 4096 deep, in one op.

Section 2 · Interactive

02The exponents do the magic: n³ math, n² memory

Work grows with n³ — every new row and column multiplies against everything else. But the data only grows with n² — you read A, read B, write C, once. Bigger matrices mean more math per byte hauled from memory. Drag n and watch the gap blow open.

Slider is logarithmic, 256 → 16384.

Section 3 · Interactive

03Two ceilings: which one do you hit?

Every GPU has a math ceiling (TFLOPS of tensor cores) and a byte ceiling (TB/s of HBM). Your operation's arithmetic intensity — FLOPs per byte — decides which one you hit first. On an H100 SXM the tipping point (the ridge) is 2000 TFLOPS ÷ 3.35 TB/s = 597 FLOPs per byte. GEMM at n=4096 sits at 1365 — comfortably on the compute side.

Square fp16 GEMM: AI = n/3, so GEMM turns compute-bound once n ≳ 1791 (n ≳ 886 against the dense peak — see the caveat below).

ridge point = peak TFLOPS ÷ memory TB/s = 2000 ÷ 3.35 = 597 FLOP/byte  ·  left of the ridge you pay bytes, right of it you pay FLOPs
⚠ A note on "2000 TFLOPS": that's the H100 SXM with-sparsity peak. Dense fp16 tensor peak is 989.5 TFLOPS → dense ridge ≈ 295 FLOP/byte. Either way, a 4096³ GEMM (AI 1365) clears the ridge by a wide margin — the conclusion doesn't change, only the utilization percentage does (section 4).

04H100 reality check: 709 TFLOPS at 4096³

Theory says a 4096³ GEMM could touch the full compute roof. Measured torch.matmul on an H100 SXM lands at 709 TFLOPS. Whether that's "35%" or "72% of peak" depends on which denominator you use — the text's 2000 is the with-sparsity figure.

Performance scales with matrix size, then plateaus around 4096³ — bigger stops helping. ~70% of the dense peak is a healthy figure for cuBLAS-class kernels; the remaining ~30% goes to tiling edge effects, partial tensor-core tiles, and DRAM latency. Production inference stacks use tuned kernels in the same league.
def benchmark_gemm(m, n, k):
    a = torch.randn(m, k, dtype=torch.float16, device='cuda')
    b = torch.randn(k, n, dtype=torch.float16, device='cuda')
    torch.cuda.synchronize()
    start = time.perf_counter()
    for _ in range(100):
        c = torch.matmul(a, b)
    torch.cuda.synchronize()
    return 2 * m * n * k * 100 / (time.perf_counter() - start) / 1e12

# H100 SXM, fp16 tensor:   2048³ -> 617 · 4096³ -> 709 · 8192³ -> 686 TFLOPS

The GPU is busy 100% of the time in all three cases — the plateau means per-FLOP efficiency peaks near 4096, not that the GPU gave up.

Section 5

05GEMM in a transformer: same weights, different M

Where does GEMM actually run in an LLM? Almost everywhere — every projection in every layer (shapes below are Llama-7B). What differs between prefill and decode is not the weight matrices but M, the number of tokens in flight — and M alone flips each op between compute-bound GEMM and memory-bound GEMV.

whereGEMM shapehow often
Q, K, V projections(M, 4096) @ (4096, 4096)×3 · 32 layers
attention out proj(M, 4096) @ (4096, 4096)×1 · 32 layers
FFN gate + up(M, 4096) @ (4096, 11008)×2 · 32 layers
FFN down(M, 11008) @ (11008, 4096)×1 · 32 layers
LM head(M, 4096) @ (4096, 32000)×1 per step

M = batch × seq_len. Prefill processes a whole prompt at once (M in the thousands); decode emits one token per sequence per step (M = batch, often 1).

While M is small, intensity ≈ M: each extra token in flight buys ~1 FLOP per byte of weights streamed. That's why batching is free throughput.

GEMM territory

Prefill · M = batch × seq_len

  • a 4K-token prompt → M = 4096
  • intensity 1365–1925 → every GEMM compute-bound
  • step cost ≈ FLOPs ÷ attainable TFLOPS — the tensor cores are the resource to optimize
  • prefill is dominated by GEMM — this whole page is the prefill cost model
GEMV territory

Decode · M = batch (often 1)

  • same weight matrices, M = 1 → intensity ≈ 1
  • memory roof caps you at ~3.4 TFLOPS — ~0.2% of the compute roof
  • each token waits for the weights to stream from HBM; tensor cores idle
  • that's a GEMV — a different beast with its own chapter (chart)

The matrix didn't change. The ratio of math to bytes did. Batch decode hard enough (b = 512+) and the GEMVs turn back into GEMMs — that's the whole game in serving.

intensity (fp16) = 2n³ FLOPs ÷ 6n² bytes = n/3 FLOP/byte  →  ridge = 2000 ÷ 3.35 = 597  →  n ≥ ~1791 ⇒ compute-bound
