Shared Memory:
the cache you control

Shared memory is a scratchpad that lives inside the streaming multiprocessor — programmer-managed, block-private, and roughly 12× closer and 7× wider than HBM. It's the key to tiled algorithms: load data once from slow memory, then reuse it across every thread in the block. The price of admission: you schedule the traffic, you place the barriers, and you share 32 banks.

~25 vs ~300cycles of latency — shared memory vs global (HBM)
15 vs 2 TB/son-chip bandwidth vs HBM bandwidth
32 banksconflict-free access = 1 cycle · 32-way conflict = 32× slower

01A scratchpad on the wrong side of no bus

L1 and shared memory share the same on-chip real estate — you choose the split, up to 164 KB per SM. Unlike a hardware cache, you decide what lands there, when it's consistent, and how it's addressed. That control is what makes tiled algorithms possible.

A block's threads share its SM's scratchpad. Threads in a different block can't touch it — and a block can't move SMs mid-flight. It's a village well, not a city reservoir.

Closer and wider: shared memory wins on both latency and bandwidth, because the data sits a few millimeters from the cores instead of across the board.

The contract: __syncthreads()

Declaring shared memory is one line — __shared__ float smem[256]; — but the data isn't ready until every thread has written its piece. The barrier is a rendezvous: all threads in the block must arrive before any of them may continue. Miss it, and reads race against writes — some threads consume whatever happened to land in time.

02Bank conflicts: 32 tellers, one queue each

Shared memory is sliced into 32 banks, word address round-robin: address 0 → bank 0, address 1 → bank 1, … address 32 → bank 0. Threads hitting different banks are served simultaneously. Threads hitting different addresses in the same bank serialize — a bank conflict. Same address in many banks? Free broadcast.

⚠ Broadcast is free, and padding is the classic fix: all 32 threads reading the same address costs one cycle (the value broadcasts). Only different addresses in the same bank hurt. When your layout forces column-like access, remap with an odd stride — or declare your tile one element wider (smem[32+1][32]) so columns land in different banks.

03Tiled reduction: the whole pattern in one kernel

Summing 256 numbers with one block shows every shared-memory rule working together. Here it is at 16 numbers so you can watch: load once from HBM, barrier, then halve the problem log₂N times entirely on-chip.

press play
🔒 __syncthreads()

16 values in smem, loaded from global memory. Watch the active region halve: 16 → 8 → 4 → 2 → 1.

// The real kernel — same pattern, 256 numbers per block
__global__ void sum_reduce(float* data, float* result, int n) {
    __shared__ float smem[256];
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    smem[threadIdx.x] = (idx < n) ? data[idx] : 0.0f;      // ① load HBM → shared, coalesced
    __syncthreads();                                        // ② everyone's data is in
    for (int s = blockDim.x / 2; s > 0; s >>= 1) {          // ③ log₂N steps, all on-chip
        if (threadIdx.x < s) smem[threadIdx.x] += smem[threadIdx.x + s];
        __syncthreads();                                    // ④ sync after every step
    }
    if (threadIdx.x == 0) atomicAdd(result, smem[0]);      // ⑤ one result crosses back to global
}

Global reads: 256 per block, once. Everything after step ② never touches HBM again — that's why the loop is log(N) cheap steps instead of N/2 slow ones.

Section 5

05Four rules for living in shared memory

Shared memory rewards structure and punishes improvisation. These are the working rules.

the pattern

Load once, reuse log N times

Move data HBM → shared with a coalesced read, then do all cross-thread work on-chip. The reduction buys log₂N cheap steps; matrix multiplication loads a tile once and reuses it across a whole row and column of outputs — the payoff that cuBLAS rides to 90% of peak.

coalesced load→log N on-chip steps→1 write back

Barrier after every dependent step

__syncthreads() after the load and after every step whose reads depend on the previous step's writes. Every thread in the block must reach it — put it where all threads execute, not behind divergent branches. Missing barrier = silent race; misplaced = deadlock.

write → readneeds__syncthreads()between

Mind the 32 banks

Consecutive indexing is automatically conflict-free. For strided or column access, remap with an odd stride (stride 17 walks all 32 banks) or pad the tile by one word — anything that keeps same-bank threads on different addresses.

smem[i*32]⇒pad +1orodd stride

Don't hoard the scratchpad

The 164 KB per SM is shared by every block that lands there — a block asking for the whole slab caps how many blocks run concurrently, and occupancy is what hides HBM latency. Budget shared memory per block like the precious, fast, tiny resource it is.

big smem/block→fewer blocks resident→latency exposed
block sum = 1 HBM load + log₂N shared steps → 300 + 8×25 ≈ 500 cycles, not 2700  ·  scale this to tiles → that's GEMM
