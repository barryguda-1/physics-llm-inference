why this kernel is slow — and what the numbers say to do

nsys showed you where the time went. Nsight Compute (ncu) puts one kernel under a microscope and answers why. Under hundreds of collected counters sit five numbers that decide the diagnosis — compute %, memory %, occupancy, L2 hit rate, bank conflicts — and one chart, the roofline, that turns them into a verdict: memory-bound, compute-bound, or latency-bound, each with its own fix.

Section 3 · Case study

03Two GEMMs, same problem, 9× apart

Same matrix multiply, same GPU, same shapes. The naive version reads every input from HBM over and over; the tiled version stages blocks through shared memory so each byte does many FLOPs. The five numbers don't just say one is faster — they say exactly what the naive one should do next.

Compute-bound at 89% of peak, 95% L2 hits, zero bank conflicts — the tiling is doing its job. Well-optimized: ship it, and profile again after the next change.

Read the saturated metric, not the starved one — the saturated bar names the bound (naive: memory), the starved bar measures the waste (naive: 88% of the compute you paid for). And note tiling lowered occupancy, 0.89 → 0.71, while going 9.4× faster: occupancy is a means of hiding latency, not a score — it only explains slowness when throughput is low too.

Section 4 · Interactive

04The roofline: one chart that names your bottleneck

X-axis: arithmetic intensity — FLOPs per byte of HBM traffic. Y-axis: performance. A kernel can never rise above min(bandwidth × intensity, peak FLOPS): a diagonal memory ceiling that climbs with intensity, then a flat compute ceiling. Every kernel lives on or under this roof. Drag the dot — the only thing you control is the intensity.

Anchor dots are measured kernels: naive GEMM holds 91.7% of its memory roof (123 of 134 TF); tiled GEMM holds 89.2% of the fp16 peak (883 of 990 TF). Real kernels sit a few percent under the line — the draggable dot shows the ideal. H100 SXM: 3.35 TB/s HBM3, 990 TFLOPS dense fp16.

Section 5

05The optimization loop

Profile → diagnose → fix → reprofile. The profiler is only half the tool; the other half is changing one thing and re-profiling to prove it mattered.

the loop

One change per experiment — then reprofile

Every fix gets a before/after ncu run and a before/after duration. Two changes at once and you can't attribute the delta; a fix without a re-profile is a rumor. Keep the profile files — profile-before.ncu-rep, profile-after.ncu-rep — the diff is the result.

profile→diagnose→fix one thing→reprofile

Memory-bound? Move fewer bytes, not faster bytes

When Memory% is saturated, no schedule trick beats physics: the fix is raising intensity. Coalesce first (last chapter), then tile through shared memory so each fetched byte feeds many FLOPs, then fuse passes so intermediates stay on-chip. Watch L2 hit rate climb toward 90% as proof.

L2 23%→tile + fuse→L2 95% · 9× faster

Both engines idle? It's latency, not throughput

Compute% and Memory% low means nothing is saturated — warps are stalled. Check occupancy next: low occupancy with low throughput is the register/shared-memory pressure signature. Shrink registers per thread, launch more smaller blocks, or fuse the kernel into a neighbor to amortize the launch.

SM 9% · Mem 22% · occ 0.18→raise occupancy / fuse

Compute-bound above ~85%? You're near done

Below 80% of peak while compute-bound, the suspect is the instruction mix: fp32 where tensor cores could run fp16/bf16, un-fused multiply-adds, div/sin where a polynomial would do. Above ~85%, further tuning buys single digits — spend the time on the next kernel, which is probably memory-bound.
