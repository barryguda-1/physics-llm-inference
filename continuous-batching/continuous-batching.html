Continuous batching:
why serving systems never wait for a batch to finish

Collect 8 requests, run them together, return all results, repeat. That's static batching — and it wastes nearly half your GPU: fast requests sit through slow ones, new requests queue behind entire batches, finished slots keep burning compute. The Orca paper's fix was almost embarrassingly simple: check after every single decode step. This page simulates both, then builds the rest of the scheduling stack — the request lifecycle, the radix prefix cache, and the paged KV memory that makes it all fit.

56%slot utilization in the book's static example
95%+utilization with iteration-level scheduling

01Static batching and its three wastes

The server collects a batch of 8 and runs until every request in it finishes. Three things go wrong: early-completion waste (a request that hits its stop token keeps its slot — the hatched blocks below), waiting waste (requests 8–23 gray out entire batches away), and padding waste (shorter prompts padded to the longest — prompt-side, not drawn here). The book's 8-request example: 900 useful tokens out of 1,600 slot-tokens = 56%. This sim runs a deeper queue of 24 requests so you can watch the waste accumulate.

02The Orca insight: schedule every iteration

Orca (OSDI 2022) called it iteration-level scheduling: after each forward pass, remove finished sequences, admit waiting ones, rebuild the batch. The batch composition changes every step and the GPU never runs an idle slot while the queue is non-empty. Press play on the same 24 requests and watch them drain before static even finishes its second batch (dashed line marks static's finish at iteration 490).

Efficiency here counts idle tail slots too: near the end the queue empties and running slots fall below 8 — under steady load (queue never empties) continuous batching holds 95%+. The mechanics that make this hard: each sequence owns a KV cache (freed on completion), attention masks must stop cross-sequence attention in the merged batch, and every sequence tracks its own position, not a batch-global one. Orca reported 36.9× throughput over FasterTransformer on GPT-3 175B — bigger gains with variable output lengths, high request rates, and larger batches.

03The scheduler: states, policies, preemption

Continuous batching made the scheduler the brain of the system: it decides who runs, who waits, and who gets kicked. Every request walks the lifecycle below — click any state to see what the scheduler knows and where its KV cache lives.

DECODING

Generating tokens one at a time; the KV cache grows by one entry per layer per step. This is where requests live almost their entire life — and where iteration-level scheduling checks for completion after every single step.

KV cache: on GPU, growing · position advances 1/step

FCFS — first come, first served

Fair and simple, but one long request can block many short ones. The baseline every scheduler starts from.

SJF — shortest job first

Minimizes average latency, but output lengths are unknown in advance — heuristics (prompt similarity, request history) estimate them.

Priority — + preemption

Latency-sensitive requests jump the queue; victims are swapped out (KV cache to CPU memory or disk) and resume without re-prefilling. Production = hybrids: priority tiers, deadline awareness, starvation guards.

  1. premium request admitted
  2. batch full → victim = lowest priority
  3. victim's KV cache swapped to CPU RAM
  4. victim re-queued at front of WAITING

05Paged KV memory: fragmentation → block tables

Sequences have unknown, variable final lengths. Pre-allocating contiguous KV space either wastes memory or fragments it into unusable holes. vLLM's PagedAttention borrows from OS virtual memory: fixed-size blocks, one block table per sequence, any free block usable by anyone.

Naive contiguous allocation fragments

Each sequence gets one contiguous run of KV memory. Step through allocations, free one, then try to fit a bigger request.

pool: 32 units · 8 free

PagedAttention blocks no fragmentation

KV cache lives in fixed 4-token blocks (vLLM uses 16). Sequences grow by grabbing any free block; waste ≤ 1 block each. Fork, then grow the fork — copy-on-write copies only the block that must change.

free blocks: 13/16

Paged attention needs kernels that follow the indirection — FlashInfer's paged kernels take the kv_indices page table directly (Chapter 6). Copy-on-write is what makes beam search and parallel sampling cheap: siblings share every block until one of them writes. In 2026 the same block tables reach off-GPU tiers — pinned CPU RAM, SSD, object stores — see §6.

Section 6 · October 2026

06Since the book: serving in 2026

Nothing on this page got old — it got promoted. Between the book's stack (Orca '22, vLLM '23, SGLang '24) and today, every idea above became either a shipping default or the foundation the field builds on. Six things that changed, each tied back to the section it grew out of.

2025 → 2026

Prefix caching became the default

The vLLM V1 rewrite (Jan 2025) ships near-zero-overhead prefix caching on by default. SGLang's radix tree now covers every model and moved to a Rust core, with branching-point caching lifting token hit-rate from 43.8% → 60.8%. Schedulers went cache-aware: vLLM now schedules requests that already hold KV blocks first.

FAST '25 → 2026

Prefill and decode moved to separate machines

The book's appendix note became the production pattern: Mooncake (Kimi, FAST '25), NVIDIA Dynamo (GTC '25), DistServe. vLLM shipped a KV-affinity router (Dec 2025), an official disaggregation guide (Sep 2026), push-based RDMA KV transfer, and bi-directional KV reuse for multi-turn agents — up to 3.3× lower TTFT.

← grows §2: the two phases are now physically split
2025 → 2026

Speculative decoding went mainstream

The appendix's "next frontier" preview is now standard equipment: MTP (DeepSeek), EAGLE-3 with a draft-training library, parallel drafting (P-EAGLE, DSpark, DFlash) and adaptive verification. In production, GLM-5.2 with disaggregation + MTP cut TPOT from 40 ms → 17 ms; DSpark sustains ~384 tok/s at acceptance length ≈ 5.

← grows the appendix preview: verify-in-parallel is everywhere
2026

The KV cache escaped the GPU

Paged blocks (§5) now span tiers: pinned CPU memory, SSD, even object stores — vLLM's tiered offloading and SGLang's runtime-attachable L3 caches. HiSparse keeps long-context pages host-resident (+58% throughput), and KV itself went low- precision: FP8 by default, NVFP4 and 4-bit on newer hardware.

← grows §5 paged memory: the block table now points off-GPU
2025 → 2026

Schedulers went async-first

Chapter 8's overlap scheduling preview became the architecture: vLLM's Model Runner V2 (default since Sep 2026) rebuilt the engine around persistent batching, async scheduling and GPU-native input prep; SGLang reached "zero-overhead" scheduling via CUDA-graphable spec-verify; DeepSeek's wide-EP setup serves at 2.2k tok/s per H200.

← grows §3: the scheduler is no longer on the critical path
2025 → 2026

Hybrid attention rewrote the caching rules

Linear/hybrid models (Qwen3-Next, Kimi K3 KDA, DeepSeek sparse attention) keep recurrent state, not plain K/V — so engines now cache internal-state checkpoints (Mamba prefill checkpoints alone give +9–25% TTFT). Decode Context Parallelism shards KV along the sequence (3× on long context), and Rubin NVL72 got day-0 support claiming 7.8× per-GPU over GB200.
