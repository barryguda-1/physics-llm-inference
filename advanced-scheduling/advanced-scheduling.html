01Chunked prefill: slice the wall

Prefill is compute-bound with time ∝ prompt length squared — a 32K-token prompt on an H100 takes 2–5 seconds, and during every one of those milliseconds the decode tokens of all other users are blocked. Chunked prefill breaks the prompt into pieces and interleaves them with decode steps. Pick a chunk size and watch the same workload re-schedule: the orange prefill row shatters into chunks, and the decoder rows below never stall for more than one chunk at a time.

Model from the book: 32K prompt ≈ 3000 ms of prefill; a 512-token chunk takes 47 ms (64 iterations); one joint decode step for the 6 requests ≈ 5 ms. Without chunking every decoder waits out the full 3000 ms — then bursts. With 512-token chunks the worst a decode token is ever delayed is one chunk: 47 ms. The pink strip is the prompt's KV cache: each chunk's attention reads all previous chunks' KV and appends its own — which is why chunking drops straight into the incremental KV-cache design. Total prefill work is unchanged; only its shape in time changes. Prefill time scales as (32K)² × 80 layers × ops / FLOPS — the quadratic is attention over the prompt. Chunk-size tradeoff: smaller → lower decode latency, more scheduling overhead; larger → better compute efficiency, higher decode latency. Production values: 256–1024 tokens per chunk.

02Mixed batches: split attention, fuse everything else

With chunked prefill, one batch can hold 512 prefill tokens and a handful of decode tokens — GEMM and GEMV, compute-bound and memory-bound, in the same step. Padded into one rectangle (the book's Figure 4, recreated left) two-thirds of the compute is spent on padding. The fix on the right: attention runs separately per kind — different KV caches, different sequence lengths — while embedding and FFN run once over the concatenated token list, because they are per-token ops with no batch dimension to mismatch.

All 514 tokens — 512 prefill + 2 decode — enter as one flat list. Nothing is padded: the "batch" is just tokens, and every per-token op can treat them identically.

Why the split lands exactly at attention: embedding and FFN are per-token operations — no batch dimension, nothing to mismatch — so they fuse over the concatenated list. Attention must be separate anyway: prefill queries attend to a growing KV cache over hundreds of tokens (a GEMM), decode queries to their own paged KV one token at a time (a GEMV). FlashInfer ships the two optimized kernels for exactly this pattern (Chapter 6): BatchPrefillWithPagedKVCacheWrapper and BatchDecodeWithPagedKVCacheWrapper. Scheduling the mix uses a token budget — max_tokens_per_step: prefill chunks are sized to leave room for decode tokens, keeping the step inside memory limits. With no padding, efficiency is 514 / 514 instead of the book's (512+1+1) / (512×3) = 33%.

03CUDA graphs: 300 launches → 1 replay

Every kernel launch costs 2–10 µs of CPU time, and a decode step issues 300+ launches. The overhead is roughly constant — so it dominates exactly where decode lives: small batches. CUDA graphs record the whole launch sequence once, then replay it with a single launch and zero CPU involvement. Drag the batch size and watch the eager CPU lane stay busy the entire step while the graph CPU lane finishes its work in a sliver.

Fixed shapes

A graph captures exact tensor shapes. Batch size or sequence length changes → a different graph. Hence the bucket ladder above and MultiShapeGraphRunner in the book.

No dynamic control flow

Data-dependent branches can't be captured — the GPU must follow the recorded path exactly, with no CPU decisions along the way.

Memory per graph

Each graph allocates its own intermediate buffers. A ladder of shapes costs real VRAM — buckets are chosen deliberately, not exhaustively.

Warmup cost

Capturing requires running the model once. The first request to hit a new shape pays for it — so shapes are pre-warmed at startup, not on the critical path.

Why decode is the sweet spot: every decode step processes exactly one token per sequence — only the batch size varies, and the bucket ladder covers it. Prefill shapes vary with prompt length, but chunked prefill (§1) makes them predictable too: a fixed chunk size is a fixed shape. Record with torch.cuda.graph(...) around the model, then per step: static_input.copy_(x); graph.replay(); return static_output.clone().

04Overlap scheduling: hide the CPU under the GPU

Someone has to decide what runs next — check completions, pick sequences, build the input tensors, update KV pointers. If that CPU work runs after the GPU finishes, the GPU idles: the book's 2 ms of scheduling against 10 ms of compute forfeits 2/12 = 17% of throughput. The fix (Figure 5, recreated): while step N runs on the GPU, the CPU prepares step N+1. Toggle the modes and drag the timings.

the CPU's 2 ms:
  1. check which sequences completed

Implementation in the book: a scheduling thread plus a lock — the run loop starts _schedule_next on a thread, forwards the current batch, then join()s before using the result. Finer-grained still: two CUDA streams — compute and transfer — so the next batch's H2D copy (non_blocking=True) overlaps compute too. Gains grow when scheduling is complex (radix matching, priority queues: 1–5 ms), batches are small, or request rates are high. Model above: overlapped throughput = 1000 × (c+s)/c → +20% at 2/10; the book's measurement lands at 1000 → 1150 tok/s (+15%). SGLang runs its scheduler on a separate thread by default.

06Since the book: scheduling in 2026

Every technique in this chapter started as a paper or a flag and ended up as a default. Six things that changed, each tied back to the section it grew out of.

OSDI '24

This chapter has a name: Sarathi-Serve

The chunked-prefill + piggybacked-decode pair (§1 + §2) is stall-free batching from Sarathi-Serve (Microsoft Research & UW-Madison): split prefills into chunks, let decodes ride along in the same batch, adapt chunk size to load. It sustained up to 2.2× the load at the same latency SLOs versus then-vLLM/Orca baselines — and every major engine adopted the idea.

← grows §1 + §2: the book's first two sections are one paper
2025 → 2026

Chunked prefill became the default

No longer an opt-in flag: vLLM's V1 engine ships chunked prefill on by default (trading a little TTFT for much better TPOT), and SGLang exposes --chunked-prefill-size with defaults in the thousands of tokens — bigger than the book's 512 because newer GPUs digest larger chunks before decode delay hurts. The knob that survived is the §2 token budget.

← grows §1: everyone now ships the 47 ms promise
2025

CUDA graphs escaped fixed shapes

The bucket ladder (§3) was the workaround; piecewise compilation is the fix: vLLM V1's default compilation mode splits the model at attention (dynamic) and captures everything else as CUDA graphs via torch.compile — graph replay without hand-curated shape lists, and full-graph capture for supported models. The book's "fixed shapes" limitation is now mostly gone.

← grows §3: replay by default, buckets as fallback
2025 → 2026

Schedulers went async-first

The book's DIY thread-plus-lock (§4) became architecture: SGLang has run its scheduler on a separate thread since v0.4.x and pushed toward "zero-overhead" scheduling — making input prep itself CUDA-graphable; vLLM's Model Runner V2 (default since Sep 2026) rebuilt the engine around persistent batching, async scheduling and GPU-native input prep. The GPU never waits for the CPU anymore, by construction.

← grows §4: overlap graduated from trick to architecture
FAST '25 → 2026

The other answer: don't share the GPU at all

Chunking shares the GPU between prefill and decode; disaggregation separates them onto different machines — Mooncake (Kimi, FAST '25), NVIDIA Dynamo, DistServe, with vLLM's KV-affinity router and RDMA KV transfer shipping since (Chapter 7 §6). Long-context and agent-heavy workloads lean disaggregated; general serving leans chunked. Both descend from the same observation: prefill and decode interfere.

← grows §1 + §2: manage the interference, or remove it
2026

The techniques compose multiplicatively

Nothing here was superseded — they stack: chunked prefill feeds the mixed batch a fixed shape, fixed shapes make decode graph-capturable, graphs shrink the CPU's per-step work to a single replay call, and overlap hides what remains. Engines that put it all together serve DeepSeek-class MoE models at ~2.2k tok/s per H200 — the Chapter 9 / Chapter 10 story.
