Memory Coalescing:
why adjacent threads must read adjacent addresses

A warp is 32 threads that request memory together. The hardware folds those 32 requests into as few transactions as the addresses allow — one if they're contiguous, thirty-two if they're scattered. Same 32 numbers, up to 32× the memory traffic. This one pattern is the difference between 89% and 23% of peak bandwidth.

Section 1

01One warp walks into a memory system

GPUs don't move bytes one at a time — memory travels in fixed-size chunks (32- and 128-byte transactions). When a warp reads, the hardware looks at all 32 addresses and issues the minimum number of transactions that covers them. Contiguous addresses collapse into one sweep. Scattered addresses can't be merged — every gap costs a transaction.

Coalesced · stride 1
thread i reads address i — adjacent threads, adjacent floats
one 128 B transaction — all 32 floats, one sweep
Strided · stride 32
thread i reads address i × 32 — adjacent threads, far-apart floats
1 transaction128 B on the wire · every byte used · warp served in one sweep
32 transactions1024 B on the wire · only 128 B used · 12.5% utilization

Each small block below the threads is one 32-byte sector (8 floats). Orange = fetched but thrown away. The hardware can't skip it: memory moves in whole chunks, whether you need the bytes or not.

// Same copy, two access patterns — the only difference is the multiply
__global__ void coalesced(float* data, float* out, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) out[idx] = data[idx];            // thread i reads address i      → 1 transaction
}
__global__ void strided(float* data, float* out, int n, int stride) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) out[idx] = data[idx * stride];   // thread i reads address i×stride → up to 32
}

Run the strided version with stride = 2 on an H100 and bandwidth drops 3.8×. Nothing else changed.

Section 3

03Where strided access hides: row-major matrices

Nobody writes data[idx * 32] on purpose. Strided access sneaks in through data layout. A row-major matrix stores rows back-to-back in memory — so reading along a row is coalesced, and reading down a column is strided. Same matrix, same amount of data, wildly different traffic.

Thread k reads A[2, k] — addresses 16…23, consecutive. 1 transaction.

⚠ The transpose trap: a naive matrix transpose reads columns and writes rows. Half of its traffic is strided no matter how you write it. The classic fix — staging tiles through shared memory so both directions coalesce — is exactly the trick the next section builds up to.

Section 5

05Four habits that keep memory coalesced

You rarely write raw strides. You inherit them — from layouts, transposes, and glue code. These are the working rules.

layout 101

Keep the hot dimension contiguous

Inference tensors are (batch, seq, hidden) with hidden last in memory. Kernels that sweep the hidden dimension — per-token GEMVs, norms, activations — then read contiguously for free. Batch-contiguous data makes batched ops coalesce too. PyTorch's default layout is usually right.

[b][s][h] · h last→coalesced reads

Distrust transposes and permutes

.transpose()/.permute() don't move data — they change the strides, so the next kernel may read scattered. Check .is_contiguous(); if a hot kernel consumes a non-contiguous view, one up-front .contiguous() copy usually pays for itself.

transposed view→.contiguous() once→fast kernel

When a kernel is slow, check the pattern first

Compute achieved bandwidth — bytes moved ÷ time — and compare to peak. Far below ~80%? Suspect access patterns before anything else. Profilers (Nsight Compute, the nsys traces from the last chapter) show sector counts and coalescing directly.

GB/s vs peak< 80%?look at strides

Let Triton and cuBLAS do the bookkeeping

Library GEMMs are coalescing-optimized to the last sector. In Triton, contiguous tl.load block pointers get you coalescing automatically — you pick the layout, the compiler handles the transaction packing. That's why it's the sweet spot for inference kernels.

friendly layout+tl.load blocks→coalesced, for free
utilization = useful bytes ÷ (32-byte sectors touched × 32 B)  →  stride 2: 128 ÷ 256 = 50% of the wire wasted — and measured bandwidth falls 3.8×
