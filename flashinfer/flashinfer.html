FlashInfer: attention built for serving, not training

FlashAttention won by refusing to materialize the N×N matrix — for training-shaped batches: fixed size, same length, contiguous tensors. A serving engine produces none of those. FlashInfer is the kernel layer built for the shapes inference actually produces: ragged batches, paged KV caches, one token at a time.

Section 1 · The setup

01Four assumptions, broken by production

FlashAttention was designed for training. Training batches are rectangles: B sequences × the same length, one contiguous KV tensor, every launch dense. Inference violates each assumption — and each violation has a bill.

broken · shape

Variable sequence lengths

Requests arrive with 50 or 5,000 tokens of context. Dense kernels want a rectangle, so the batch is padded to its longest request: the mask hides the ghost cells from the softmax, but the memory is allocated and the kernel still walks them.

padded to max → 55% of this batch is ghost
broken · layout

Paged KV cache

PagedAttention stores each request's cache in small blocks scattered across HBM — that's what kills the O(B · max_len) pre-allocation. But standard attention kernels can't even index it: they expect one contiguous tensor per sequence.

one sequence's logical pages 0–3 → wherever free HBM was
broken · phase

Prefill and decode are different workloads

Prefill processes the whole prompt: T queries against T keys — GEMM-shaped, tensor-core territory. Decode processes one new token: a single query row against the entire cache — GEMV-shaped, pure bandwidth. No one kernel shape is optimal for both.

T×T
1×N
prefill's score tile vs decode's score row
broken · schedule

Batched decode

A serving step runs dozens of sequences in one forward pass — each at its own position, each with its own context length, all sharing one launch. Kernels must consume per-sequence metadata instead of batch-uniform shapes.

1 step = 32 seqs · lens 64 … 2048 · 1 launch
Section 2 · Interactive

02Ragged tensors: the rectangle tax, made visible

Padding is easiest to see in one picture. Pick a batch, then flip between the layout a dense kernel wants and the one FlashInfer consumes. One array — indptr — replaces the whole mask: indptr[i] says where sequence i starts, and the kernel reads kv[indptr[i] : indptr[i+1]]. Nothing else exists.

The same trick pays twice: no ghost memory and no mask tensor. The kernel's thread count is derived from the indptr array, so every scheduled token is a real token — at batch assembly time, not inside the kernel. Decode batches are the extreme case: every query row is exactly one token, so qo_indptr is just [0, 1, …, B].

Section 3 · Interactive

03The paged KV cache: contiguous is a fiction

Logically, each request's cache is one contiguous tensor. Physically, PagedAttention keeps it in small pages wherever free HBM was, and a page table — kv_indices — maps logical block i to a physical page. The kernel gathers pages through that table; the block manager allocates in O(1); waste is bounded by one partial page per request. Step a batch through decode and watch the pages scatter.

HBM · 64 pages × 4 tokens (toy size; real systems: 16)
page tables · one row per live request
Press decode step — each step appends one token to every live request. Watch what happens when a request crosses a page boundary.

Compare with the alternative: reserving [B, max_len] contiguous cache per sequence up front. That reserves B · max_len · 2 bytes × layers × KV heads before the first token arrives — so the batch size and context length are capped by a worst case that mostly never happens. Pages turn that into on-demand allocation with ≤ 1 page of slack per request and zero external fragmentation — freed pages are instantly reusable, no compaction.

Section 4 · Interactive

04Prefill is a GEMM. Decode is a GEMV.

Same operator, opposite physics. Prefill's arithmetic intensity grows with prompt length until tensor cores saturate. Decode streams the entire cache to produce a single token and never leaves the memory wall: with GQA 32/8 its intensity is 4 FLOPs/byte at every context length (each K/V byte feeds 4 query heads — 1.0 without GQA). That split is why FlashInfer ships two wrappers, not one.

Section 6 · Walkthrough

06Two wrappers, one workspace, one plan per step

Everything above — ragged indptr, the page table, prefill vs decode — lands in a small integration pattern. Walk through what happens once at startup and what happens every serving step:

# once, at engine startup
workspace = torch.empty(32 * 1024 * 1024, dtype=torch.uint8, device="cuda")
prefill = flashinfer.BatchPrefillWithPagedKVCacheWrapper(workspace)
decode  = flashinfer.BatchDecodeWithPagedKVCacheWrapper(workspace)

# every engine step, for the requests in this batch
decode.begin_forward(
    qo_indptr  = qo_indptr,   # ragged queries — decode: [0, 1, …, B]
    kv_indptr  = kv_indptr,   # where each sequence's KV starts and ends
    kv_indices = kv_indices,  # the page table from the block manager
    num_qo_heads=32, num_kv_heads=8, head_dim=128)
out = decode.forward(q, kv_data)   # one fused launch over scattered pages
step 0 / 5
Press play — startup first, then one serving step.

Modern FlashInfer splits the planning call into wrapper.plan(...) + wrapper.run(...) — same split: CPU-side scheduling, GPU-side execution. The kernels are Jinja-templated CUDA, JIT-compiled at first call for your head_dim, dtype and layout. SGLang runs FlashInfer as its default attention backend; vLLM and MLC-LLM integrate it as an option. FlashAttention-3 itself was co-designed with it.

Section 7

07Four habits for the serving path

You will never write these kernels — you'll feed them, and keep them on the fast path. Four habits that decide whether you actually are:

Never pay for padding

Assemble batches as ragged indptr arrays, not padded rectangles — for queries, KV, and anything else with variable length. The mask approach spends real bandwidth on ghost tokens; indptr spends one integer per sequence.

pad to max · mask→indptr · 0 ghost cells

Page the cache, preallocate nothing

A contiguous [B, max_len] cache reserves B·max_len·2 bytes × layers × KV heads before the first token arrives — that cap, not the kernel, limits your batch. Pages allocate on demand in O(1) and waste at most one partial page per request.

[B × max_len] reserved→pages on demand · ≤1 page slack

Plan once per step, reuse across layers

qo_indptr, kv_indptr and kv_indices are identical for every layer. Call begin_forward once per engine step and share the plan across the whole model — planning per layer burns CPU inside the loop you're trying to keep GPU-busy.

1 plan→all L layers

Pick the kernel for the phase

Prefill is a tensor-core GEMM; decode is a bandwidth problem — so batch aggressively (same memory system, more users) and let split-KV schedules spread long caches across SMs. Then keep the habit from the FlashAttention chapter: bench achieved GB/s, not FLOPs.

prefill: max FLOPsdecode: max B/s

08What's new: Hopper → Blackwell → Rubin

The integration pattern above is now the stable part. What moves is everything around it: every release lands the newest NVIDIA silicon and the newest model architectures as kernels. The last month shipped three:

v0.7.2Oct 15, 2026
  • Rubin (SM107) support — MoE experts and DeepSeek-V4 sparse MLA run on Rubin via the cuDNN "Frost" CuTe DSL backend (BF16, MXFP8, NVFP4).
  • DeepSeek-V4 NVFP4 sparse-MLA decode on B200/B300 through the new backend="cake"; prefill paths for RTX PRO 6000 / RTX 5090.
  • Fused-epilogue GEMMs — FP8/NVFP4 linear + SwiGLU, and QKV + QK-norm + RoPE, fused into single kernels (prims_ts).
  • Speculative decoding — multi-token verify rows auto-route to cuDNN on B200/B300.
v0.7.1Oct 9, 2026
  • Quantized expert-parallel MoE — NVFP4/MXFP8 on Rubin SM107; SM12x W4A16 reported 1.36× faster than Marlin on DGX Spark.
  • Kimi K3 fused speculative verification — +1.8–3.3% vLLM throughput on 8×B300; cuDNN linear-attention prefill for KDA / Gated DeltaNet on Blackwell.
  • DeepSeek-V4.1 dual-cache sparse MLA; compact 528-byte KV rows for GLM NoPE checkpoints (~19.5% smaller).
  • plan()/run() formalized — the CPU/GPU split from section 06, with backend reuse across calls.
v0.7.0Sep 22, 2026
  • Unified MoELayer API + MegaMoE — fused expert-parallel MoE kernels get the "one library" treatment attention got in 2024.
  • Autotuner v2 — tunes the way you serve, with persistent caching across runs.
  • Experimental-API policy — a published stability contract for everything else.
Read together, the releases confirm the bet this page opened with: the ragged / paged / plan-run contract is stable while everything around it churns — new silicon (Hopper → Blackwell → Rubin), new architectures (DeepSeek sparse MLA, Kimi KDA/Mamba2, sparse MoE), new formats (FP8 → MXFP8 → NVFP4). "Inference-specific kernels" now means far more than attention — but qo_indptr, kv_indices and a workspace are still the whole interface.
