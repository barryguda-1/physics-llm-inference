The Generation Loop:
how an LLM writes one token at a time

You type a prompt. The model reads all of it at once — then writes the answer one token at a time, feeding each new token back in to pick the next. That feedback loop splits every request into two totally different jobs: a parallel prefill and a serial, cache-driven decode. This page walks you through both, the wasteful naive way of doing it, and the KV cache that fixes it.

def generate(model, prompt_ids, max_tokens):
    input_ids = prompt_ids.clone()
    for _ in range(max_tokens):
        logits = model(input_ids)               # re-runs the WHOLE sequence, every step
        next_token = torch.argmax(logits[:, -1, :], dim=-1)
        input_ids = torch.cat([input_ids, next_token.unsqueeze(-1)], dim=1)
        if next_token.item() == eos_token_id: break
    return input_ids

Correct, and quietly O(n²) wasteful — the next section counts exactly how wasteful. Every token you've ever read from a chatbot was born in a loop exactly like this one.

02Why the naive loop throws away almost all its work

To write token 100, the naive loop re-processes tokens 0–99 — but the attention values for tokens 0–98 are exactly the same as when it wrote token 99. It's like re-reading a 300-page book from page 1 every time you add one word to your book report. Count the orange below: it's almost all redundant.

Section 3

03Two phases, one model — two different bottlenecks

Same weights, completely different jobs. Prefill reads your whole prompt in one giant parallel gulp — that's a matrix-times-matrix (GEMM), dense math the GPU loves. Decode then writes one token per pass — a tiny vector-times-matrix (GEMV), where the GPU mostly just moves bytes. Different shapes → different bottleneck.

Prefill compute-bound

one pass · all prompt tokens at once

The whole prompt is known upfront, so every token is processed in parallel: a big (p × d) × (d × p) attention computation. Every weight the GPU loads gets reused across all p rows → tons of math per byte → the tensor cores stay hot. Bigger prompts, proportionally more math: efficient.

Decode memory-bound

step 0 / 64 — one token at a time

Only the newest token needs logits, so each pass is a (1 × d) vector against every weight matrix. Each weight is read from memory, used once, thrown away → almost no math per byte. The compute units sit idle waiting for data to arrive over the memory bus. The GPU is a brilliant chef whose ingredients arrive one spoonful at a time.

Section 4

04The KV cache: take notes, don't re-read the book

Here's the first big idea of LLM inference. Each token's keys and values depend only on that token itself — once computed, they never change. So compute them once during prefill, write them into a cache, and from then on every decode step just appends one new row and glances at the notes. That's what turns generation from O(n²) into O(n) per token.

Left: without a cache, step k re-processes all k previous tokens — cost grows every step. Right: with a cache, every step processes exactly one new token; the history is looked up, not recomputed.

The cache fills one row per token

pre-allocated buffer · slots used: 0/10

Each new token appends its K (purple) and V (pink) to every layer's cache. The new token's query is dotted against all cached keys, and its output is a weighted sum of all cached values — attention over history without recomputing history.

⚠ The cache isn't free — it's the memory hog of production inference.
Each token adds a K and a V to every layer: 2 · layers · kv_heads · head_dim · 2 bytes per token ≈ 0.1–0.5 MB for a 7B-class model. One 4K-token conversation ≈ 0.6–2 GB — per user. Multiply by thousands of simultaneous users and you see why serving systems obsess over cache memory management.
def decode_attention(q_new, k_cache, v_cache, k_new, v_new):
    k_cache = torch.cat([k_cache, k_new], dim=-2)   # append 1 new row — that's the whole trick
    v_cache = torch.cat([v_cache, v_new], dim=-2)
    scores  = q_new @ k_cache.transpose(-2,-1) / math.sqrt(q_new.shape[-1])
    return torch.softmax(scores, -1) @ v_cache, k_cache, v_cache

Shapes tell the story: q_new is (1, d) against k_cache (s, d) — one row against the whole history. A GEMV against the cache, a GEMM against nothing else.

05Why decode wants batching

At batch size 1, every single token requires reading all ~15 GB of weights from GPU memory — a whole grocery-trip truck to deliver one item to one house. Batch B requests together and the same one trip delivers to B houses: the weights are read once and shared. Bonus: with B rows instead of 1, your vector × matrix quietly becomes a matrix × matrix again — GEMV turns back into GEMM, and the arithmetic intensity multiplies by B.

one decode step = one read of all weights, shared by every request in the batch

Real servers do this continuously: vLLM and SGLang re-fill the batch the moment any request finishes (continuous batching). Throughput climbs until the GPU's compute saturates — past that point you're trading latency, not buying speed.
