Kernel Launch Overhead:
why tiny kernels destroy decode throughput

Every CUDA kernel launch pays a fixed 2–10 µs tax on the CPU side — before a single FLOP happens. For big kernels it's a rounding error. For the hundreds of tiny kernels in every LLM decode step, it quietly eats double-digit percentages of your throughput.

01Anatomy of one kernel launch

When you call a CUDA kernel, the work doesn't start immediately. Six things happen — and the first four happen on every single launch, no matter how trivial the kernel is.

For a kernel that runs 100 µs, steps 1–4 are a rounding error. For a kernel that runs 1 µs, they're catastrophic.

# Measure it yourself: 10K single-element adds — compute ≈ 0, so we time pure launch overhead
x = torch.randn(1, device='cuda')
torch.cuda.synchronize()
start = time.perf_counter()
for _ in range(10000):
    y = x + 1
torch.cuda.synchronize()
overhead_us = (time.perf_counter() - start) / 10000 * 1e6   # typical: 3–8 µs

Typical result: 3–8 µs per launch — that's the fixed tax, measured.

03The decode problem: ~340 launches per token

Autoregressive decoding of a 7B model is thousands of tiny memory-bound kernels. Generating one token touches every layer's projections, norms, and glue ops:

96GEMV calls · 32 layers × 3 FFN projections (gate, up, down)
64norm calls · 32 layers × 2 normalizations
~50miscellaneous · rotations, residuals, sampling, copies…
attention GEMV ×128 FFN GEMV ×96 norms ×64 misc ×~50 each dot = one kernel launch = one launch tax

04Eager launches vs CUDA Graph replay

A CUDA Graph records the entire decode step once — every kernel, allocation, and dependency — then replays it with a single launch. Same kernels, same math, no per-kernel tax.

Same 340 kernels. Same math. The graph finishes ~1.45 ms sooner per token — roughly +17% decode throughput from deleting waiting time alone.

Illustrative: 22 blocks shown, each standing in for ~15 of the ~340 real launches. Slow-motion ~550×. Blue = kernel executing, orange = launch overhead.

g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    output = model.decode_step(input, kv_cache)   # recorded once

for token in range(max_tokens):
    g.replay()                                     # one launch, whole step
⚠ The caveat: graphs can't handle dynamic shapes. If batch size or sequence length changes, you need a new graph. Production systems pre-record graphs for the shapes they actually serve.
Section 5

05Four ways to fight launch overhead

For inference, CUDA Graphs are the standard answer — but they're not the only tool.

standard for inference

CUDA Graphs

Record the whole decode step once, replay it with a single launch. Per-kernel overhead drops to near zero. Caveat: static shapes only — pre-record graphs for the shapes you serve.

record→replay ▶▶▶≈ 0 tax

Kernel fusion

Combine multiple small ops into one kernel. Instead of add then multiply, write a single fused add-multiply kernel. Fewer launches and less memory traffic.

add→mul⇒fused add·mul

Operator batching

Instead of launching a separate norm kernel for every layer, batch all 32 norms into one kernel. Same op, one launch instead of 32.

32 × norm⇒1 × batched norm

Persistent kernels

Keep one kernel running and feed it work through shared memory or atomics. Advanced technique for specific workloads — the kernel never exits, so it never relaunches.

kernel ⟳ resident←work fed in
