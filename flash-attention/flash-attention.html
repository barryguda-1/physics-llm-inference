FlashAttention:
never materialize the N×N matrix

Standard attention computes the N×N score matrix, writes it to HBM, reads it back for the softmax, writes the normalized weights, reads them again — 4N² round trips to memory that make attention memory-bound long before the math is. FlashAttention's insight is simple: tile Q, K, V into SRAM-sized blocks and carry the softmax online — a running max and sum that rescale as blocks arrive — so the N×N matrix never exists anywhere. vLLM, SGLang, TGI, and every serious inference engine runs on this trick.

01The N² problem: a matrix too big for the chip

Attention's intermediate is N² elements — at fp16 and N=4096 that's 32 MB per head, against ~192 KB of SRAM per SM. So the scores live in HBM, and every stage of attention pays to reach them. Drag the sequence length and watch where the matrix stops fitting.

vs 80 GBHBM3 · 3.35 TB/s — where it actually lives—
scores: 16.8M elements per head: 32 MB across heads: 1.0 GB per layer

Fit cells are optimistic by design: L2 is a shared, streaming cache — a 32 MB score matrix competes with the other 31 heads' matrices and the K/V traffic flowing through the same 50 MB. If it doesn't fit easily, treat it as HBM round trips.

# the whole problem, in three lines
def standard_attention(Q, K, V):
    scores  = Q @ K.T / math.sqrt(d_k)   # N×N — must go to HBM: SRAM is ~200 KB
    weights = softmax(scores, dim=-1)     # read N², write N²
    return weights @ V                    # read N² again

Every intermediate is N² elements, but no on-chip memory can hold them — that single mismatch is what FlashAttention removes.

03Online softmax: softmax without seeing the whole row

The blocker to fusing attention is the softmax: it needs the row max and the sum of every exponent — a global reduction over a row you'd have to fully materialize first. The fix is to carry the reduction online: keep a running max m and running sum ℓ, and when a new block raises the max, rescale everything computed so far by e^(m_old − m_new). Watch it process x = [2, 1, 4, 3] two elements at a time.

# streaming softmax — the heart of FlashAttention
m, l, u = -inf, 0.0, 0.0
for block in blocks(x):                  # never hold all of x at once
    m_new = max(m, block.max())            # ① raise the max
    alpha = exp(m - m_new)                  # ② how wrong were we?
    l = l * alpha + block.sum(exp(x - m_new))
    u = u * alpha + (exp(x - m_new) * v).sum()  #    rescale old + add new
    m = m_new
return u / l                              # ③ normalize once, at the very end

Why the running max matters twice over: e^x overflows fp32 above x ≈ 88, and attention scores after the 1/√d scale regularly get there. Subtracting m keeps every exponent ≤ 0 — numerically safe by construction, not by luck.

Why the rescale is exact — and what it costs

One identity does all the work. When a new block raises the max, every exponent computed so far can be rebased to the new max without being recomputed:

e^(x − m_old) = e^(x − m_new) · e^(m_old − m_new)

The α factors telescope: block 0's terms get multiplied by e^(m₀−m₁), then by e^(m₁−m₂)…, which collapses to e^(m₀−m_final). Every element ends up measured against the one final max, so ℓ is exactly Σ e^(x−m_final) and u/ℓ is exactly the true softmax-weighted output — for any block size: two values at a time, a 128-row K-tile, or the whole row at once. The block boundaries are invisible in the answer.

standard safe softmax
max pass · sum pass · divide pass — 3 full reads of a row that must sit in memory first
online softmax
one streaming pass — max, sum, and output together — then one divide at the end

In FlashAttention, u is the Br×d accumulator O, and the division is deferred until the Q-tile finishes — normalize once, not per block. The final (m, ℓ) pair is the logsumexp, L = m + log ℓ: the forward pass writes it to HBM so the backward pass can recompute attention tiles from Q, K, V instead of ever storing the N² matrix — training memory drops from O(N²) to O(N). And the price of the trick is just a couple of extra multiplies per element — noise next to the 4N² HBM round trips it removes.

04The tiled kernel: outer loop Q, inner loop K/V

FlashAttention wraps online softmax in two loops: one thread block per Q-tile (outer), streaming K/V tiles through SRAM (inner). The score tile S is computed, consumed, and discarded entirely on chip; only O — N×d — is ever written. Play through one 4×4 grid of tiles.

m = full(Br, -inf); l = zeros(Br)   # per Q-tile state
O = zeros(Br, d); load Q_i → SRAM
for j in range(N // Bc):              # stream K, V
    load K_j, V_j → SRAM
    S = Q_i @ K_j.T / sqrt(d)        # Br×Bc, on chip
    m_new = maximum(m, rowmax(S))
    P = exp(S - m_new)               # all exponents ≤ 0
    alpha = exp(m - m_new)           # rescale old state
    l = alpha * l + rowsum(P)
    O = alpha * O + P @ V_j          # rescale + accumulate
    m = m_new

O = O / l[:, None]                   # normalize once
store O_i → HBM                     # the only attention traffic

06Four habits that keep attention off the memory bottleneck

You will never write the tiled kernel yourself in production — every serious stack ships it. Your job is to make sure you're actually on the fused path, and to recognize the memory-bound signature when you're not.

do this

Never materialize attention

Call the fused kernels: torch.nn.functional.scaled_dot_product_attention, flash-attn, or FlashInfer. vLLM, SGLang, and TGI route through them by default. The eager softmax(Q@K.T)@V path still exists in every framework — and it still pays the 4N² tax. One flag, whole-matrix traffic gone.

eager · 4N² HBM→sdpa / flash-attn · 0

Tile until it fits in SRAM

FlashAttention is GEMM tiling plus one extra idea (the online rescale). Any op whose intermediate dwarfs the ~192 KB SRAM budget is the same bug: chunk it, carry running state, and fuse. The tile sizes (Br, Bc ≈ 64–128) aren't magic — they're what fits next to the rest of the kernel's working set.

N×N in HBM→Br×Bc tiles in SRAM

Stream reductions with a running max

Online softmax generalizes: any global reduction over data bigger than cache (norms, logsumexp for sampling, top-k) can run streaming with running state + rescale. The α = e^(m_old − m_new) correction is exact — same answer, any block size — and subtracting the running max keeps every exponent ≤ 0, so fp32 never overflows.

m, ℓ, u+α-rescale→exact · overflow-safe

Bench IO, not FLOPs

Profile with nsys/ncu and compare achieved GB/s against the 3.35 TB/s ceiling. Slow attention is almost never the math — it's traffic (an eager path, a layout that defeats coalescing) or occupancy. For decode, where one query attends over a long KV cache, ask for FlashDecoding: it splits the KV length across SMs the same way.
